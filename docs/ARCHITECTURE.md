# アーキテクチャ

## 何を解いた設計か

九九版と長さ版を独立に作った結果、**約8割が同一コード**になった。
認証・ランキング・キャッシュ・排他制御・キー配置・未送信データの退避——
どれも単元とは無関係な仕組みなのに、単元ごとに複製されていた。
3つ目を作れば、バグ修正のたびに3か所を直すことになる。

そこで **共通エンジン（Core）と単元定義（Unit）に分離**した。
新しい単元を作るときに書くのは、原則 `Unit.gs` 1枚だけになる。

```
共通エンジン ── 認証 / 出題の配信と再採点 / 記録 / ランキング / 分析の器 / 画面
      ↑
   単元定義 ── モード一覧 / 1問の作り方 / 分析の軸
```

## 依存の向き

Core は Unit を知らない。Unit が Core の期待する形に合わせる。
逆向きの依存を作らないことで、単元を足しても Core が肥大しない。

```
Core.gs  ──uses──▶  UNIT (グローバル定数)
index.html  ──uses──▶  boot() が返す設定（単元名・モード一覧）
```

## 出題の統一形式

すべての単元が、この1つの形で問題を表す。これが分離の要。

```js
{
  t:   'A',                       // 問題型。分析の軸になり、画面側の表示分岐にも使う
  q:   ['1200', 'm'],             // 出題の表示トークン
  f:   ['km', 'm'],               // 答えの欄と、その単位
  ans: { km: 1, m: 200 },         // 正解
  tag: '1200m',                   // 重複回避と分析用の識別子
  ruler: { from:0, span:85, at:64 },  // 任意。あれば目盛りを描く
  rows: [['73','÷','8','='], ['八','_','_'], ['73','-','72','=','_']],  // 任意。並べ方を単元が決める
  veil: 2                             // 任意。n番目以降の欄がある段を、そこに着くまで覆う
}
```

- 単位が要らない単元（九九）は `f: ['']` とし、単位ラベルを空にする
- `ruler` があれば Core の画面が SVG で目盛りを描く。長さ以外（重さ・かさ）でも使える
- `q` に `+` `-` `×` `÷` を混ぜると演算子として描画される
- `q` の中で `UNIT.units` のキーと一致するトークンは単位として描画される。
  画面（`index.html`）は単位名を知らないので、**単元が持つ単位はすべて `UNIT.units` に列挙する**
  （例: `{ km: '#F1B1E4', m: '', cm: '#8A6CE5' }`。色は学年ごとに使ってよい別学年の色から選ぶ（docs/ADD_UNIT.md「学年の色」）。空文字で既定色）
- `t` は画面側が型判定に使う（例: 2段組にするか、ふりがなの案内を出すか）。
  桁数や `ruler` の形から画面側が型を推測してはいけない。推測は必ず外れるケースを生む

## 式の並べ方を単元が持つ

既定の描画は **「式 ＝ 欄」に固定**されている。`q` が左辺に並び、答えの欄は必ず右端に集まる。
この形では作れないものが2つある。

- 答えが左に来る形（`□ ＝ 4 × 8`）
- 欄が式の途中や複数の段に散る形（`八 □ □` ／ `73 − 72 ＝ □`）

**共通画面に単元ごとの分岐を足して解くと、依存が逆流する。** 以前 `index.html` が
「モード5は2桁」という長さ単元固有の分岐を持っていたのと同じ失敗になる。
そこで `digitCap` と同じく**単元が宣言する**形にした。問題が `rows` を持てば、
共通画面はその並びのとおりに描くだけで、意味は知らない。

`veil: n` は「n番目以降の欄がある段を、そこに着くまで覆う」。
覆いの向こうに**前の段の答えを使って書いた式**を置けるようにするためのもので、
先に読めると手続きを飛ばして答えが出てしまう段を隠す。

このため、**覆いより手前の欄は正解でないと越えられない**。既定の欄移動は
「上限桁まで打てば進む」だが、それだと誤った値のまま次の段が開き、
その段の式と画面の中で食い違う。打ち切った時点で1回のまちがいとして落とす。

`UNIT.slotColor` は欄キーごとの「目立たせる色」で、宣言された欄に
色・下線の太さ・薄い塗りをまとめて付ける。**色だけに意味を持たせない**という決まりを
共通画面の側で守るため、3つは分けて指定できない（単元が色だけを宣言することはできない）。

`UNIT.glyph` は欄キーごとの字形の表で、宣言された欄の数字だけその字で描く
（九九の商を漢数字にするなど）。打つのは数字キーのままで、判定も記録も数字。
`digitCap` と同じく宣言であって、答えは含まない。

## 判定の方式

| 方式 | 使う場面 | 例 |
|---|---|---|
| 欄ごとの一致 | 位に分けること自体が目標 | 1200m = □km□m |
| 合計での一致 | 値を読むことが目標 | まきじゃく（1m87cm も 187 も正解） |

`UNIT.byTotal(item)` が true を返す型は合計で判定する。
空欄は 0 として扱うので、`0km400m` と「km欄を空にして400」が両方通る。

## 自動判定と情報漏れ

答えの桁数が確定していれば、Enter なしで自動確定できる。
ただし**桁数そのものがヒントになる**ため、出題側で桁数を揃える責任を負う。

- 2欄の m 部は常に3桁にする
- 引き算の答えを `□km□m` にするなら 0km も出す（1km以上かを漏らさない）
- 桁数が揃えられない場合は Enter 確定にし、画面に案内を出す

**確定に使う桁数は `UNIT.digitCap` で宣言する。** Core はこの宣言だけを見て、
その問題の実際の答え（`ans`）は参照しない。

```js
digitCap: { 1: { '': 2 }, 5: { cm: 2 } }   // モードid → 欄キー → 桁数
```

実際の答えの桁数で確定させると2つ壊れる。1つは、桁数の大小が
「早く確定する／しない」という形でヒントに変わること。もう1つが重い。
**答えが1桁の問題は1打で確定し、2桁の問題は2打かかる。
主指標である所要msに、問題の種類ごとの打鍵数の差が混入する。**

九九がこれを踏んでいた。9×9 の積は1〜81 で、1桁の答えが81通り中23通り（28%）。
1桁の答えを多く含む段（1・2の段）だけが速く見えていたが、
それは想起が速いのではなく打鍵が1回少ないだけだった。
`weak_child` は段ごとの平均想起時間を主指標にしているので、
この下駄は分析の結論を直接ゆがめる。

`digitCap` が無ければ従来の「正解の桁数 or 欄の上限」で確定する。
既存単元との互換のために残してあるが、新しい単元では必ず宣言する。

**この宣言を Unit 側に置いたのは依存の向きを保つため。** 以前は `index.html` に
「モード5は2桁、モード6は3桁」という長さ単元固有の分岐が直接書かれていた。
共通画面が特定の単元のモード番号を知っている状態で、
他の単元が `ruler` を使うと壊れる。宣言に置き換えて解消した。

## セキュリティ

| 脅威 | 対策 |
|---|---|
| スコアの改竄 | 点数を送らせない。解答だけ送り、サーバーがシードから問題を再生成して再採点 |
| 他人になりすまし | トークンにメールを紐付け、送信時に照合 |
| 制限時間の詐称 | 制限時間をセッション開始時の値としてトークンに固定 |
| シートの直接編集 | デプロイを「実行＝自分／アクセス＝ドメイン内」にし、児童に権限を渡さない |
| 教師画面への侵入 | 教師ドメイン（`@edu.nishi.or.jp`）・所有者・`config.teachers` のみ |

完全ではない。開発者ツールを開ける児童は突破しうる。
`log` に1問ごとの所要msが残るので、全問200ms未満のような異常値は事後に検出できる。

### 教師の判定はドメインの完全一致で行う

教師は `@edu.nishi.or.jp`、児童は `@kyoiku.edu.nishi.or.jp`。
**児童のドメインは教師ドメインのサブドメインになっている。**

```
tanaka@edu.nishi.or.jp          → 教師
a1234@kyoiku.edu.nishi.or.jp    → 児童（教師ではない）
```

`indexOf('edu.nishi.or.jp') >= 0` や `endsWith('edu.nishi.or.jp')` で書くと、
**児童が全員教師になる**。`weak_child`（誰がどの型で遅いか）まで児童の画面から開けてしまい、
README が「児童に見せない前提」としているものが崩れる。

`@` の右側を切り出して `TEACHER_DOMAIN` と完全一致で比べる（`isTeacherDomain_`）。
`config.teachers` は例外の口として残す。別ドメインの教師（支援員・非常勤など）を1件ずつ足す。

判定はサーバー側だけで行い、教師画面の URL は教師と判定したときにしか
児童画面へ渡さない。児童のブラウザにリンクの文字列自体が届かない。

## モードの公開

**どのモードを児童に見せるかは、教師がクラスごとに指定する。**
`class_config` シートが `class | mode_1 | mode_2 | … | seq_off` を持ち、
チェックの入ったモードだけが児童の一覧に出る。

以前はこれを「フラグ」で持っていた。単元が `flags` を宣言し、
モードが `flag: 'calc'` のように1つのフラグを参照する形で、
フラグは学年で自動的に開き、クラスごとに上書きできた。
**この形は、モードよりフラグが粗いため要求に応えられない。**
複数のモードが同じフラグを共有するので片方だけ閉じることができず、
`flag: null` のモードには閉じる手段がそもそも無い。
実際、4単元20モードのうち単独で閉じられるものは1つも無かった。

学年による自動の解禁も廃した。担任が触っていないのにモードが開いている状態を作らない。
どのモードを出すかは進度の判断で、学年から機械的に決まるものではない。
**初期状態は全モードがオフ**なので、設置後に教師画面で開く操作が要る。

`Unit.gs` は公開の可否を持たない。単元は「どんなモードがあるか」だけを宣言し、
「どれを使うか」は現場が決める。

### 公開が0件のときだけ、児童画面が取り直す

`boot()` は起動時の1回しか呼ばれない。教師が授業中に公開しても、
画面を開いたままの端末は再読み込みするまで空のまま残る。
帯活動の途中で40人に「もう一回ひらいて」と言わせるのは、公開の操作としては使えない。

そこで **公開が0件のときだけ** 15秒ごとに `boot()` を取り直す
（`index.html` の `watchRun`）。1件でも開けば見張りは止まり、以後は通信が増えない。
プレイ中の画面と、ふたを閉じた端末（`document.hidden`）では叩かない。
**負荷は「まだ開いていない端末の数」で頭打ちになり、教師が公開した瞬間に0へ戻る。**
40台が同じ授業の頭に開くと巡回の秒が揃うので、間隔に0〜5秒のばらつきを足してある。

10分（40回）で打ち切る。閉じたまま放置された端末が一日中叩き続けるのを防ぐため。
打ち切ったあとは案内文を「さいど よみこんで ください」に替え、
タブに戻ってきた操作（`visibilitychange`）を「まだ待っている」の合図として数え直す。

## 順次開放

型を積み上げる単元（あまりのあるわり算の ①九九さがし → ②誤答判別 → ③わり算）は、
前のモードを一定回数やるまで次を開けない。`Unit.gs` が宣言する。

```js
{ id: 2, needs: { mode: 1, tries: 3 } }
```

Core は `needs` という形だけを見る。単元名も型名も入らない。

**条件を「回数」にしてある。**「①で n 問以上」のような成績条件にすると、
到達バッジを却下したのと同じ欠陥が戻る——閾値の適正値が学級ごとに違い、
上位層はすぐ開き、下位層は最後のモードに永久に到達しない。
回数なら遅い子でも必ず到達し、順序だけが担保される。

`class_config` の `seq_off` にチェックを入れると、そのクラスだけ順序を外せる。
授業で全員に同じモードをやらせる場面があるので、担任が上書きできる口を残す。
この列は `needs` を持つ単元の教師画面にだけ出る。

- 回数は summary の `tries` を合算する。制限時間も本番／練習も問わない
  （「何回やったか」の条件を、制限時間の設定で塞がないため）
- **順序待ちのモードは画面に出す。** 消すと「順番にやる」こと自体が児童に伝わらない。
  薄く表示して「「九九さがし」を3かい やると あきます」と添える。
  対して**教師が非公開にしたモードは一覧から消す**。閉じている理由が違う
  （「まだ」なのか「このクラスでは使わない」なのか）ので、見せ方を分ける
- 名簿にない利用者（ゲスト）は記録が無いので全部開ける。
  名簿にない児童も「おためし」として全モードを使える——記録しないのだから、
  使わせない理由が無い。対象はログインしている全員（教師ドメインに限らない）
- 判定はサーバー側でもう一度行う（`startSession` / `nextPracticeItem`）。
  `localStorage` の古い控えで開いて見えても通らない

## 教師が触る設定

共通の設定（制限時間・閾値など）は `BASE_DEFAULTS` にある。
単元固有の設定は `UNIT.settings` で宣言すると、教師画面に欄が自動で生まれる。

```js
settings: [{ key: 'ruler_tape', label: 'テープの太さ', min: 60, max: 200 }]
```

Core も `teacher.html` も key の意味を知らない。宣言した単元にだけ欄が出る
（長さの巻き尺設定は九九の教師画面に出ない）。欄を直接 `teacher.html` に
書き足すと、共通画面が単元を知ることになり依存が逆流する。

**設定は表示にだけ効かせる。** `gen` は `rand` と `mode` しか受け取らない。
教師が変えた値で出題が変わる作りにすると、サーバーの再採点と食い違ってスコアが壊れる。
長さの巻き尺で「表示範囲（span）」を設定項目にしていないのはこのため。
span は目盛りの窓と答えの値域の両方を決めているので、表示だけを変えられない。

## 背景の床（成長する図形）

最初のメニューの背景に、練習を重ねるほど育つ非周期の床を敷ける。
単元が `settings` で `floor_on`（onoff）と `floor_per_answer`（1正答あたりの育ち）を宣言したときだけ動く。
図形は単元が `UNIT.floorPattern` で選ぶ（`FLOOR_PATTERNS_` の id。既定は `penrose`）。
今は九九（八角の星）・あまりのあるわり算（ペンローズ）・長さのたんい（巻き尺の渦）・おもさ（円弧の曼荼羅）・円と球（円と球：起点2つ）が宣言している。
タイルは穴（`h`）を持てる。画面に掛かるかはタイルの外接する四角で判定する。
タイルは育つ順の値（`o`、0〜1）も持てる。`o` を持つ図形は、育ち始める点からの距離ではなく `o` の順に育つ（起点が複数の図形。
円と球は、円の模様と球の模様それぞれの中の距離の順位を枚数で割った値で、2つが同じ割合ずつ交互に育つ）。①の先のにじみは枚数（次の60枚）で付ける。
生成器は design リポジトリの `growing-figures/generators.js` を `common/index.html` に写したもの。直すときは向こうを正本にする。宣言の無い単元では `uset_` が 0 を返し、キャンバスは隠れたまま何も計算しない。
図形・育ち方・色の正本は design リポジトリの `growing-figures/`。ここにあるのはその実装。

- **育ち方**：無地 → ① 輪郭線 → ② 太い菱形を学年の色で塗る → ③ 細い菱形を第二の色で塗る。
  どの層も「育ち始める点」から外へ広がり、画面全体を覆い終えたら次の層へ進む。菱形は必ず1枚まるごと描く
- **育ちやすさは「標準の分数」で揃える**（`floorPace_`）。
  床の枚数 ＝ 標準の分数 × 20 × `floor_per_answer`。標準の分数 ＝ Σ（モードごとの本番の累計正答 ÷ そのモードの1分あたり平均正答）。
  20 は基準の速さ（1分20問。`FLOOR_REF_PER_MIN_` と画面の `FLOOR_REF`）。1正答の枚数は `floor_per_answer × 20 ÷ そのモードの平均`。
  基準をサイトの平均にしないのは、サイトをまたいで「解きにくいほど染まりやすい」を保つため。
  1分あたり平均正答は、このサイトの `summary` の本番の行（全児童・全制限時間）から出す。
  年度初めに値が暴れないよう、1分20問を10分ぶんの事前値を足してから割る（単元が `floorPrior` で変えられる）。
  解きにくい問題を載せたサイト・モードほど1問で多く育ち、平均的な速さなら1分の練習でどのサイトも同じだけ育つ。
  練習（記録しない・時間制限つき）は入れない（★と同じ理由）
- **画面側**：本番を記録できた時に `正答 ÷ そのモードの平均` を足し、`localStorage` の控えも書き換える
- **色**：第一は学年の色。第二はサイトごとに変え、`UNIT.floorColor` で `FLOOR_GEMS_`（宝石の名の8色）から選ぶ。
  薄く塗る背景で意味を伝える色ではないので `GRADE_EXTRA_` には縛らない。学年の色と同じ色は `validateUnit_` が落とす。
  サイトごとの割り当ては design リポジトリの `growing-figures/COLORS.md` が台帳
- **軽さ**：描くのは状態が変わった時だけ。同じ色・濃さの菱形を1本のパスに集めて1回で塗る。
  床の計算はメニューを出した後に回す。育つ演出は、本番を終えてメニューに戻った時に、増えた菱形だけを描き足す。
  起動直後やサーバーの値で追いついた時は演出しない
- **見返し**：メニューの左下に ▶ のボタンを1つ出す（床が少しでも育っている時だけ）。1回目で無地に戻し、押すたびに今の育ちの 1/6 ずつ、
  本番のあとと同じ演出で広げる。6回で今の育ちに戻り、次はまた無地から。見せ方だけで控えにもサーバーにも触れない。
  メニューを離れると見返しをやめて今の育ちを描いておく。重さは本番のあとの演出1回と同じ（押した時だけ動く）
- **教師画面のプレビュー**：床を宣言した単元では「設定」タブに、児童の Chromebook（1366×768）と同じ図形・同じ2色の床を縮めて描く箱が出る。
  「1正答あたりの育ち」の入力欄を書きかえると保存前に反映し、「全部そろうまで約◯問（1分20問の速さで）」を出す。
  生成器は2つ目の写しを置かず、`index.html` の `'FLOOR_GEN_BEGIN';`〜`'FLOOR_GEN_END';`（何もしない文）の間を Core.gs の `floorGenForTeacher_` が切り出して
  `teacher.html` に埋め込む（貼るファイルは4つのまま）。design から写し直すときも印は残す。
  印をコメントにしてはいけない：GAS の include（HtmlService の getContent()）は JS のコメントを消して返すため、サーバーから見えなくなる
- **文字の際**：タイトル・カード・ボタンから10pxの範囲で模様を薄める（菱形ごとに距離から濃さを決める）
- 表示だけの仕組みで、出題にも採点にも関わらない

## 協力モード

クラス全員の本番の正答で1つの図形を育てる、教室の大画面（教師画面の「きょうりょく」タブ）だけに出す仕組み。
児童の画面はいつものまま（左上に自分の色のエンブレムと「協力プレイ中」が出るだけ）。
印は画面（section）の外に置くので、メニュー・結果・プレイのどこに居ても出る（明るい画面では白い札）。
教師が始めたときに開いたままの画面にもすぐ出すため、児童側は**画面を触っている間だけ**10秒＋ばらつきごとに
`coopPeek`（自分の色に必要な分だけ返す軽い問い合わせ）を聞く。無操作が5分続く端末・閉じた端末は聞かず、
次の操作や画面への復帰で即1回聞いて再開する（恒常的な通信を増やさない）。変化がある時だけ印を描き直す。

- **始め方**：「全画面でうつす」→ 図形の画面の中央の「開始」→ 5→1→スタート。開始ボタンはステージの中の1つだけ
  （開始前は選んでいる図形の下地を下見として映す。終わった図形を映している間は時計の下に小さく出す）。
  始まりはサーバーが `now + COOP_COUNTDOWN_MS`（5秒）に置き（`coopStart({ countdown: true })`）、画面はその `start` と
  サーバー時計のずれ（応答の `now`）から数字を出す。始まりを先に決めるので、混雑で開始に失敗しても「スタート」を出す前に分かる。
  数えている表示は送信中の印とセッションの `start` だけから決めるので、ページを開き直しても同じ表示に戻る。
  リセットも同じく数えてから始める。制限時間はスタートから数え、カウントダウン中に遊び終えた回は数えない。
  countdown を渡さない呼び出し（古い画面）は今すぐ始まる。やりとりの形は後方互換なので ENGINE_VER は上げない。
  全画面はブラウザごと（`requestFullscreen`。タブとアドレスバーも消す）。断られたらページいっぱいの表示で続ける。
  全画面の間の Esc は keydown に届かないので、`fullscreenchange` で元の表示に戻す
- **1正答の枚数（自動）**：終わりに完成（最小の縮尺 0.32 で画面の9割）の85%まで育つ枚数にする（`coopAutoRateOf`）。
  完成を越えると以後の正答が画面に出ず「解いても何も起きない」になるので、見込みが外れても越えにくい側を狙う。
  枚数 ＝ 0.85 × 完成の枚数 ÷ 見込みの正答。完成の枚数は画面の大きさと図形から数える（`coopFinalTiles`。箱と全画面で違い、
  枚数もそれに合わせて変わるので、育ちの割合はどちらで見ても同じ）。見込みの正答 ＝ 人数（氏名の空いた人を除く）× 参加 0.9 ×
  遊べる回数（予定の分 × 60 ÷（1回の秒 ＋ 25秒））× 1回の正答（`coopPace_`：サイト全体の本番の1分あたりの正答。床と同じ下駄つき）。
  参加 0.9 と間の25秒は根拠のない仮定。保存した回を再生しながら「1正答」を書きかえると終わりの形を試せるので、実際の回で確かめて直す。
  速さ・予定の分・1回の秒はセッションと保存データに持たせ、再生でも開始時と同じ枚数になる。
  入力欄に数を入れるとその数で固定（画面の大きさを変えても変わらない）、空にするか「自動にもどす」で自動に戻る
- **名前の表示**：ステージ左上の「名前をかくす／名前を出す」で下の名札を切り替える（モニターに名前を出したくない時）。
  見る人の端末ごとに localStorage に覚える（読めなければ出す）
- **同期**：提出1件（本番の1プレイの `submitSession`、ロックの内側）を、ライブのイベント列キャッシュに1件足す（シートには書かない）。
  教師画面は3秒ごとに `coopState(since)` で差分だけ取り、そのときにまだ書いていない分を `coop_log` へまとめて1回で書く（`coopFlush_`）。
  クラス全員が同じ1分の終わりに送るので、提出ごとのシートへの書き込みがロックの時間を延ばし、混雑で弾かれる提出を増やしていたため。
  まとめ書きも同じロックを取るが、0.5秒で諦めて次の回に回す（提出を待たせない）。
  教師画面が閉じている間はまとめ書きが起きないので、書いていない分が40件を超えたら提出の側でも書く（キャッシュが消えたときに失う分を限る）。
  キャッシュが消えてサーバーの列が手元より短くなったら、教師画面は差分をやめて全件を取り直す
  児童側に push は要らないので「教師画面だけに反映」の設計にした
- **育ち**：1提出＝その児童の色の連続パッチ（生の正答数 × 教師画面の「1正答の枚数」）。
  タイルは育ち始める点からの距離順に貪欲に割り当てる。画面の9割が塗れたら縮小（×0.72、最小0.32）して外へ育て続ける
- **打ち切り**：締め切りは届いた時刻ではなく、その回を**遊び終えた時刻**（`startSession` が置いた開始時刻＋制限時間）で見る。
  協力の開始から終了＋10秒（カウントダウンと通信の遅れ）の間に遊び終えた回を数え、終了から10分を過ぎて届いたものは数えない。
  混雑で弾かれた提出は次の起動で送り直されるが、届いた時刻で見ると終了後になって数えられず、混んだ瞬間に送った子に片寄るため。
  遅れて届いた回は、画面の時間軸では終了の時点に置く（再生の順が崩れない）。
  次の協力を始めても、直前の協力はその10分の間 `coop_prev` に残し、直前の協力の中で遊び終えた回の送り直しはそちらへ数える
  （締め切り直後に「開始」を押すと、前の回の取りこぼしが出ていた）。リセットで途中から切り直したときは、前の協力の終わりをその時点にする。
  締め切り後に増えた合計は、教師画面の問い合わせで `coop` シートの行にも追いつかせる
  `coopState` が時刻を見て自動で done に閉じるので「おわる」の押し忘れでも閉まる
- **練習は入れない**：`!isPractice` の内側だけで `coopNote_` を呼ぶ。分析と同じ理由
- **色**：シードで決まる決定的な割り当て（index.html と teacher.html に同じ式を写す）。児童の順序（名簿の番号順）は
  サーバーと画面で同じなので、児童は自分の index だけで自分の色を復元できる
- **組**：教師が児童ごと⇄グループを選び、組の割り当て（`gi[]`）を名札のタップで編集する。
  保存データは児童 index 単位のままで、組は表示時の写像。保存時と今の組、どちらでも見られる
- **同時セッションは1つ**：`coop_live` キャッシュがライブの1件、`coop` シートは履歴。リセット＝新しいセッション id で始め直す
- **キャッシュが消えても続く**：`coop_live` が期限前に消えたら、`coop` シートの最後の行（児童の並びは名簿、合計は `coop_log`）から組み直す。
  セッションが1つも無いときは `null` を置き、起動のたびにシートを読みに行かない
- **ロック**：教師の操作（開始・終了・組の編集・時刻での打ち切り）は、提出（`submitSession`）と同じスクリプトロックの内側で `coop_live` を書き換える。
  重なると後から書いた方が前の変更を消すため（提出が組の編集を古い組で上書きする、など）。取れないときは「混んでいます」を返す
- **採点を巻き込まない**：`submitSession` の中の `coopNote_` は try に包む。協力モードで失敗しても、採点の記録は成功として返す
- **児童の印**：本番だけ。れんしゅうでは出さない（数えないので）。終了時刻を過ぎたら、教師画面が開いていなくても出さない。
  残りが1回分（制限時間−10秒）より短いときに始めた本番は、時間内に終わらず数えないので、印を薄くして「数えません／協力の 時間ぎれ」にする
  （`startSession` の `coop.counts`）。グループの色づかいでは「あなたの組の色」
- **エラーに見えるところは理由を出す**：数え方の規則は変えず、画面で説明する。モニター（児童向け、ひらがな）と手元（教師向け）に分ける。
  - 開始から最初の1回が終わるまで何も増えない → 「さいしょの 1かいが おわると そだちはじめます」
  - 残り1回分を切った → 「いまから はじめる かいは かぞえません」
  - 締め切り直後 → 「さいごの かいを あつめています」、手元には送り直しの受付の残り時間と「保存はそのあとに」
  - 参加人数（n / N人）と、名簿で氏名が空の人数は手元だけに出す（誰が遊んでいないかをモニターでクラスに見せない）
  - 組を編集したとき → 児童の画面の色は、その子が次に本番を始めたときに変わる
- **再生**：イベント列が決定的なので動画でなく「再生」として持つ。終了後・保存したものは、シークバーと倍速で最初から見直せる
  （セーブデータ＝再生データ）。終わりへの位置送りは終わりを受け取った最初の1回だけ（3秒ごとの応答で、シークした位置を戻さない）。
  巻き戻している間に届いた送り直しは列に足すだけで、見ている途中の形には割り込ませない。シークの右端は終わりそのもの
- **名簿の個人情報**：画面に出すのは番号と名だけ。`coopState` の応答からメールアドレスは落とす

## 起動の速さ

GAS はサンドボックスの起動と `boot()` の1往復（300〜800ms）が終わるまで応答しない。
以前はその間 `show()` が呼ばれず、児童は**真っ白な画面**を見ていた。
実時間以上に遅く感じる構造で、遅さの体感の大半がこれだった。

対策は2つ。

- **前回の `boot()` 結果を `localStorage` に控え、次回は先に描いてから上書きする。**
  2回目以降はメニューが往復ゼロで出る。初回は「よみこみ中…」を出し、空白は見せない
- 控えが古くてモードが多く見えても、`startSession` の `modeAllowed_` が弾く。
  表示だけが最大1往復ぶん古くなる

控えは単元ごとに分けて持つ（キーに `UNIT.id` を入れる。`doGet` がテンプレートとして評価するときに `APP_ID` として埋め込む）。
以前はデプロイURL（`location.pathname`）で分けていたが、GAS のウェブアプリはどの単元も iframe の中の同じパス（`/userCodeAppPanel`）で動くので分けられず、
あまりのあるわり算を開くと九九の控えが先に描かれ、サーバーの応答が失敗すると九九のまま残っていた。未送信の記録（`km_pending_<単元>`）も同じ理由で単元ごとに分ける。

**画面を描く処理は、DOM要素が無くても落ちないように書く。** 起動時の1行が例外を投げると、
以降が全部止まって白画面になり、原因も見えない。実際 `$('apptitle')` という
存在しない id への参照（正しくは `class="apptitle"`）が1つあり、これで全画面が死んでいた。

## 転送量について

`QN = 200`（1セッションの出題数）は多く見えるが、実測で1セッション7〜15KB。
`ruler` を積んでも問題にならない。遅さの原因をここに求めない。

## 同時アクセス（40人想定）

- **記録される試行（本番・時間制限つき練習）は、セッション中の通信がゼロ**。
  開始時に問題列をまとめて受け取り、判定も採点もローカル
- 書き込みは終了時の1回だけ。`LockService` で直列化
- **記録しない練習（むせいげん）だけは例外。** 1問ずつ `nextPracticeItem` を呼ぶ。
  採点にも ms の測定にも使わない画面なので、通信コストの制約対象ではない。
  1問だけ先読みしておくので、体感の待ちは出ない（詳細は `common/index.html` の `pServe`）
- 結果画面はローカル採点で即座に描画し、送信は裏で走らせる
- 送信に失敗した試行は `localStorage` に退避し、次回起動時に再送
- `config` と `roster` はキャッシュ（60秒 / 300秒）。ロック保持時間を縮めるため

代償：設定変更の反映が最大5分遅れる。教師画面の保存でキャッシュを破棄して即時化できる。

### 上限は「同時実行30」。これが設計を決めている

Apps Script の同時実行は**1ユーザーあたり30**。このアプリは「実行＝自分（所有者）」で
デプロイする（児童にスプレッドシートの編集権を渡さないため、これ以外に選べない）。
つまり**40人ぶんの実行が全部、所有者ひとりの30枠を奪い合う**。

学級の人数が枠を超えているので、余裕は「1実行あたりの短さ」でしか作れない。
守っている規則は3つ。

1. **シートの全読を人数ぶん繰り返さない。** `summary` と `daily` は
   メール別・クラス別に畳んだ索引をスクリプトキャッシュで共有する
   （`summaryIndex_` / `top3_`）。読むのは最初の1実行だけ
2. **待つ実行を作らない。** ロック待ちの実行も枠を占有する。
   準備処理は取れなければ諦め（`tryLock(0)`）、記録は10秒で諦めて端末に送り返す。
   教室で先に壊れるのは記録ではなく「始められないこと」
3. **開いただけの実行で書き込まない。** 書式の指定もシートへの書き込みなので、
   起動経路から外す

枠を超えた実行がどう失敗するかはクライアントからは見えないので、
**失敗を握り潰さない**ことも同じくらい重要。起動は指数バックオフで取り直し、
問題列の到着待ちは15秒で打ち切る（`common/index.html`）。

## データモデル

すべての単元で同じ。単元ごとに別のスプレッドシートを持つ。

| シート | 書き手 | 内容 |
|---|---|---|
| `config` | 教師 | 制限時間・閾値・教師メール |
| `roster` | 教師 | email / 学年 / 組 / 番号 / 氏名 |
| `class_config` | 教師 | クラスごとに公開するモード（`mode_1`…）と順次開放の解除（`seq_off`）|
| `log` | アプリ | 1試行1行。誤答と遅答だけ問題単位で圧縮して記録 |
| `daily` | アプリ | 当日ランキング（学級 × モード × 制限時間） |
| `summary` | アプリ | 累計と自己ベスト（児童 × モード × 制限時間） |
| `weak_child` | 集計 | 児童 × 問題型 の平均想起時間 |
| `weak_class` | 集計 | 問題型ごとの誤答数と、よくある誤答の一覧 |
| `coop` | アプリ | 協力モードの履歴（id / クラス / 図形 / seed / 組 / 名・番号 / 開始・終了 / 状態 / 合計） |
| `coop_log` | アプリ | 協力モードの提出イベント（session / t / email / correct / mode） |
| `coop_save` | 教師 | 協力モードの保存データ（再生そのものの payload JSON） |

**記録・分析の対象は、名簿に email と氏名の両方がある児童だけ。**
名簿にないアカウント（名簿未登録の児童・氏名が空の行）はゲストとして
全モードを使えるが、トークンを発行しないので送信も通らず、シートには何も書かれない。
集計も同じ名簿条件で log を絞るので、名簿から氏名を消した児童の過去分は
weak_child / mistakes からも消える（log の行自体は残る）。

**1試行1行にした理由**：問題単位で全部残すと40人×3回×5日で週18,000行になり、
1年で破綻する。正解は集計値で持ち、誤答と閾値超えの遅答だけを1セルに圧縮すれば
週600行に収まる。

**主指標を所要msにした理由**：既習事項の習熟を測るので、正答率は早期に天井に張り付き
児童間の差が消える。差が出るのは想起にかかる時間。

## 分析の軸

`UNIT.types` が分析の列を決める。九九なら「段」、長さなら「問題型」。
長さ版は加えて**よくある誤答の実物**を集計する。
1200m を「12km 0m」とする1000倍のずれのように、
誤りが型を持つ単元では、誤答の中身が指導の的を直接示す。

## 2種類の評価

順位だけだと、上位3名以外には何も残らない。個人内評価を並置する。

| | 何を測る | 記号 | 更新 |
|---|---|---|---|
| **学級内** | 当日の学級順位1〜3位 | 🥇🥈🥉（絵文字） | 当日リセット |
| **個人内** | 自己ベストを塗り替えた回数 | ★n（ミントの文字、1〜99） | 累積・下がらない |

記号の種類（絵文字と文字）で見た目を分けてある。

**到達バッジ（一定点数で段階が上がる）にしなかった理由**：
閾値の適正値が学級ごとに違い、上位層はすぐ天井、下位層は永遠に最低段階になる。
それは学級内順位と同じ欠陥を、個人内評価の顔をして持ち込むことになる。
更新回数なら**遅い子でも伸びれば必ず増える**。

★は本番だけ加算する。練習で増やすと意味が薄れる。

## 練習モードの記録

練習は原則として記録しない。ただし
**時間制限あり かつ ランダム出題**のときだけ、本番とは別枠のハイスコアを残す。

- 段や範囲を絞った練習は記録しない（ランダムどうしでないと比較できない）。
  ただしこの機能自体、現状は未実装（下記）
- 無制限練習は記録しない（時間が違えば比較できない）
- ランキングには入らず、`log` にも書かない（分析が濁るため）

**記録する練習（時間制限あり）は `startSession` を通す。** クライアントに
点数を自己申告させる経路を作らないため。`practice: true` を渡し、サーバーが再採点する。

**記録しない練習（むせいげん）は `nextPracticeItem` で1問ずつ受け取る。**
採点も記録もしないので `startSession` のようなトークン・キャッシュは不要。
それでも出題自体は必ずサーバーが作る。クライアントに出題ロジックを
持たせると `docs/ADD_UNIT.md` が明記する既知バグ（サーバーとの二重管理）を再発するため。

**練習で範囲を絞る機能（`practiceNarrow` / `genNarrow`）は削除した。**
以前この2つを `UNIT` に定義できる予約があったが、`index.html` 側の受け口
（段選択画面・絞り込み引数）が存在せず、機能していなかった。
復活させる場合は絞った練習を記録しない前提で、選択画面と
`nextPracticeItem` への引数から作り直すこと。

## シートの読みやすさ

生ログは機械可読を優先した形なので、教師がそのまま読むには向かない。
以下を分離した。

- **モード名の列**：log / summary / daily に「モード名」列を持つ。`mode=3` だけでなく
  「わり算(9×9)」と文字でも分かる
- **時間は秒表示**：weak_child の平均想起時間は ms ではなく秒（`3.2秒`）で表示する。
  「遅い」の色は秒の固定閾値ではなく、同じ学年・同じ型の児童の分布と比べて付ける（次節）
- **タブの色分け**：緑＝分析用（summary / weak_child / weak_class / mistakes）、
  グレー／青＝内部用（log / daily / config / class_config / roster）
- **各シートA1に注記**：セルにマウスを乗せると、そのシートの見方が出る
- **mistakes シート**：誰が・どの問題を・何と間違えたかを1行1件で並べる。
  wrong_items（誤答の記録）に正しい答えも含めるようにし、
  `UNIT.fieldsByType` があれば単位つきで表示する（例："1/200" → "1km200m"）

`fieldsByType` はオプション。答えが単一値でよい単元（九九など）は省略でき、
その場合は値をそのまま表示する。

## ハブ

単元が増えると入口が分からなくなる。ハブは**リンク集**に徹する。

- 教師画面でリンクを追加・編集・並べ替え・表示切替
- 児童には**自分の学年に該当するものだけ**を大きなカードで出す
- 名簿はハブを正本とし、各単元は `IMPORTRANGE` で参照する（三重管理を避ける）

意図的に入れていないもの：**児童の画面に出す**進捗表示、達成バッジ、履歴。
ハブが重くなるほど「入口」としての速さが失われる。

### 単元横断のぶんせき（教師の一部だけ）

`Analysis.gs` / `analysis.html`。要件は `docs/ANALYSIS_REQUIREMENTS.md`。
入口の速さを守るため、**児童の経路（`doGet` → links、`boot`）には一切載せない**。

- 集計は夜間のトリガー（`nightlyAnalysis`、1時台）。各単元の `log` の**未処理の行だけ**を読み、
  児童×単元×型×週の表 `an_facts` に足し込む（読んだ位置は `an_sources` の cursor）
- 閲覧は `?page=analysis`。開けるのは所有者と `config.an_analysts` だけ。
  ハブの `isTeacher_` はドメイン一致なので、単元横断の児童別データには使わない
- 単元のシートには書かない。型の名前は単元が自分の `meta` シートに書き（教師画面を開いた時と setup の時だけ）、ハブはそれを読む。
  ハブは別プロジェクトなので `UNIT.types` を直接は読めない
- log の読み方（`typeStat_` / `splitCellItems_`）はハブに写してある。共通ファイルに切り出すと
  全単元の設置ファイルが増えるため。`tests/analysis.test.cjs` が同じ入力で Core と同じ結果になることを確かめる
- 比較は同じ学年の全児童（名簿の学年）。帯・持続・伸びの基準は `config` の `an_*`

### ハブを学年ごとに分けるとき

ハブを学年（低・高など）ごとに分けて管理する場合、名簿の正本も学年ごとのハブに分かれる。
各単元の `roster` は縦積みで取り込む：

```
={IMPORTRANGE("低学年ハブのURL","roster!A:E");IMPORTRANGE("高学年ハブのURL","roster!A:E")}
```

縦積みでは各ソースの**ヘッダ行が途中に混ざる**。名簿を読む処理は必ず
`rosterRows_()`（Core.gs）を経由する。`@` を含まない行（ヘッダ・空行）はここで捨て、
呼び出し側が自分で判定しないこと（読み取り口を1つにしておけば、積み方が変わっても
単元は無関係でいられる）。

**同じ児童が複数ハブに載ったとき**：同じメールの行は1人に畳む。正本は先に現れた行。
ただし先の行が氏名なしで後の行が氏名ありなら後の行を使う
（記録・分析の対象になる児童を消さない）。クラス別の人数も重複カウントしない。
同学年の違う児童（別ハブの3-1同士など）はそのまま併合される——
実際に別の集団を同じクラス表記で載せる設計なら、クラス側で区別する。

### 名簿は年度ごとに残す

同じ児童でも年度が違えば別の記録・集計対象（去年は3-1、今年は4-2）。
名簿は年度ごとに分けて残す：

- `roster` … **現在年度**のライブ名簿（IMPORTRANGE や手入力）。児童の利用判定もこれ
- `roster_2025` … **過去年度**のアーカイブ

**年度替わりは自動**：毎朝走る `rolloverRoster` トリガーが 4/1 にだけ動き、
`roster` の中身を `roster_<前年度>` へ「値」として退避し、`roster` を空に戻す。
A1 が IMPORTRANGE などの式なら式を戻すので、ハブ側が新年度に更新されれば
名簿はそのまま流れ替わる。`roster_<前年度>` が既にあれば何もしない（手動で
残しておいた年度名簿を上書きしない）。

ぶんせきの過去年度表示は `roster_<年度>` があればそこから名簿を読む。
無い年度は `log` の行が持つ「記録時点の学年・組・氏名」から名簿を組み立てるので、
アーカイブが無くても過去年度は正しいクラス所属で見られる
（ただしその年度に**一度も記録の無い児童**は組み立てられない）。

## Unit.gs の契約検査

単元が増えると、宣言の欠落や gen の返り値のずれが入り込む。
`validateUnit_()` が宣言と実働の両方を点検する（エディタからは `checkUnit()`、
`setup()` の末尾でも走る。教師画面の読み込み時にも同じ結果が警告として出る）。

「注意：」で始まる行は設計上許容されるもの（digitCap の未宣言欄など）で、
残りは直すべきもの。テスト側では `tests/contract.test.cjs` が apps/ 配下の
全単元にこの検査を掛けるので、新しい単元は置くだけで契約テストに入る。

## 版ずれの検知

設置は4ファイルの手動貼り付けなので、「Core.gs だけ古い・index.html だけ新しい」
の組み合わせが起きる。Core.gs は応答に `ENGINE_VER` を載せ、画面側は自分の
`WANT_VER` と比べて、ちがっていれば画面に警告を出す。
片方にだけ依存を増やす変更（画面が Core の新しい応答を前提にする、またはその逆）では
両方の番号を一緒に上げる。

## 拡張するとき

新しい単元を足す手順は `docs/ADD_UNIT.md` を見る。
`Unit.gs` を1枚書き、Core と index をコピーして貼るだけで動く。
単元を足したら `node tests/contract.test.cjs`（または `setup()` / `checkUnit()`）で
宣言と出題の形を機械検査できる。

Core を変えるときは、**単元固有の知識を Core に入れない**こと。
「長さのときだけ」という分岐が Core に現れたら、それは Unit に置くべきもの。

名簿や設定など、**シートの読み取り口を増やさない**こと。
`rosterRows_()` のように1つの関数に寄せておくと、データの取り込み方が変わったとき
（例：名簿の縦積み）直す場所が1箇所で済む。


## 遅いの判定

「遅い」は秒の固定閾値で決めない。**同じ学年・同じ型**の児童の分布と比べる（`Core.gs` の `slowBand_` ほか）。
型ごとに打鍵数・手順の数が違うので、1つの秒数では型によって赤が出すぎたり出なかったりする。

| 段 | やり方 | 理由 | 根拠 |
|---|---|---|---|
| 1回ごとの時間 | 対数に直す | 反応時間は遅い側に長く裾を引く。平均が裾に引っぱられる | Ratcliff (1993)：外れ値の処理として、観測を捨てない変換（対数・逆数）を推奨 |
| 児童の代表値 | 対数の平均＝幾何平均 | ときどき大きく遅れた回（よそ見・数え直し）で代表値が動かない | 同上 |
| 学年・型の中心と広がり | 中央値と MAD×1.4826 | 平均・SD は数人の極端な値に引っぱられ、その極端な値自体を見落とす。MAD は崩壊点 0.5 | Leys et al. (2013) |
| 段階 | 頑健な z で ≤0／≤1／≤2／>2 | ×1.4826 で正規分布なら SD と同じ目盛りになる。偏差値＝50−10z（速いほど高い） | 同上 |
| 1回の中の飛びぬけて遅い問題（slow_items） | 対数で 中央値＋2.5×MAD 超 | 論文の既定値 | Leys et al. (2013) |
| 本人の中で遅い型（◆） | 本人の偏差値の中央より10以上低く、かつその型の偏差値の標準誤差の2倍を超える | 個人内の差は2つの値の誤差が両方乗り、見かけの凸凹が出やすい | McDermott, Fantuzzo & Glutting (1990) ほか、下位検査のプロフィール分析への批判 |

### 根拠の無い値（実データで見直す）

- `SLOW_MIN_KIDS_ = 10`：比べる児童の最少人数。中央値・MAD が数人で決まらないようにした保守的な値
- `SLOW_MIN_TRIES_ = 5`：児童の代表値を使う最少回数。ゆらぎの判定（5回）にそろえた
- `SELF_GAP_DV_ = 10`：◆の差（偏差値10＝1σ）

### この方式の限界

- **学年全体が遅い型には色が付かない。** 相対比較なので、学年のほとんどが手間取る型は見えない。
  学年全体の指導が要る型は、秒そのもの・誤答数・型どうしの推移で見る
- **＋1σ超は、分布がどうであれ学年の約16%前後に出る。** 「赤＝未習熟」ではなく「学年の中で遅いほう」と読む。
  海外の算数の流暢性スクリーニングでは、地域内の下位25パーセンタイルを支援の目安にする運用が多い（局所ノルム）。
  棒グラフの児童名には、偏差値と並べて「遅いほうから何%」を出している
- **古い log 行（対数の和が無い）** は、その行の平均の対数で代用する。その行の中のばらつきは0として扱うので、
  ◆の標準誤差はやや小さく出る。30日の窓を過ぎれば新形式だけになる
